## Goal

Turn one-off bills into a household's running expense history: the core
expense model every later milestone builds on (balances and settling up
in M5, export and sharing in M6).

**What the user sees at the end:**

- The Household tab opens the household they used last, or offers to
  create one.
- A household has a name, members and expenses. Several households can
  live on one device (a flat and a holiday group), and one can be
  archived.
- An expense is added in one of two ways:
  - **a quick expense:** an amount split equally, by shares, by exact
    amounts or by percentages;
  - **an itemised expense:** the existing split, with its receipt
    scanning and person-first assignment, saved into the household.
- Whoever paid can be any member, including one who isn't in the split.
- The Expenses tab lists everything, newest first, with filters and a
  search.
- Every expense can be edited or deleted.
- Everything stays on the device and survives a reload and an app
  update.

**What does not change:**

- The split maths (`split.ts`), the money rules (`lib/money.ts`), the
  receipt reader and parser.
- The quick split without a household. It still works exactly as today,
  with its draft in `settle.bill`.
- The CSP and the privacy guarantees: no new origin, nothing leaves the
  device.

## Evidence (before planning)

- **Today's storage** is `localStorage` only:
  - `settle.bill`: the split draft, `DRAFT_VERSION` 1 (`draft.ts`);
  - `settle.receipt`: the receipt summary, `RECEIPT_VERSION` 1

  date (`F`), the gross total (`O`), the document type (`D`) and the ATCUD
  (`H`), which identifies a Portuguese fiscal document. Today the import
  keeps the NIF as `merchantTaxId` and drops the ATCUD (`toBill.ts`:548).
- **`ReceiptSummary`'s reader** ignores fields it doesn't know and reads
  optional strings from a list of keys. So an optional field can be
  added without bumping `RECEIPT_VERSION`.
- **The Household page** is a placeholder (`HouseholdPage.tsx`).
  `/finances` redirects to it.
- **The design canvas, household overview:**

## Decisions taken in this plan

### H1 — IndexedDB, through a small wrapper of our own

**Storage.** The ledger lives in IndexedDB, through a thin wrapper in
`app/src/data/db.ts`. No library, the same choice M3 made for i18n:
- the API we need is a handful of calls;
- a library would add code to every page load for little gain.

**Database.** It is named `settle`, at version 1, with these object
stores:

| Store | Key | Indexes |
| --- | --- | --- |
| `households` | `id` | — |
| `members` | `id` | `byHousehold` (`householdId`) |
| `expenses` | `id` | `byHousehold` (`householdId`), `byReceiptKey` (`[householdId, receiptKey]`) |
| `meta` | `key` | — |

- **Record version.** Every record carries `v: 1`, its own format
  version.
- **Transactions.** Each user action is one `readwrite` transaction.
  Saving an expense writes one record.
- **Referential integrity (M-I-3).** IndexedDB has no foreign keys, so
  the repositories enforce one contract, inside the write's own
  transaction:
  - **saving or updating an expense** opens one `readwrite` transaction
    over `households`, `members` and `expenses`. In it, the repository
    re-reads the household (it must exist) and every member the expense
    names: the payer, each split member and each itemised mapping. Each
    must exist in that household. Only then does it write. A missing
    reference aborts the transaction, writes nothing and returns a named
    error. The UI shows "Someone on this expense was removed in another
    tab. Check the people and save again.";
  - **deleting a member** opens one `readwrite` transaction over
    `members` and `expenses`. It deletes only when it can **prove** no
    expense names the member, and otherwise aborts with a named error
    (M-I-4):
    - the scan reads the **raw** records with a cursor over the whole
      `expenses` store, not the readers' output. A record the reader
      skips is never taken as proof of no reference;
    - a raw record is cleared only if it reads and validates and names
      no such member (payer, split member or itemised mapping), or its
      raw `householdId` is a string naming a **different** household;
    - **any other record fails closed:** an unreadable or
      unsupported-version record of this household, or one whose
      `householdId` is missing or malformed, blocks the delete. The
      member page then says "Some expenses in this household couldn't be
      read, so this person can't be deleted. Mark them as left
      instead.";
    - the failed delete changes nothing: the member and every raw record
      stay byte for byte;
  - IndexedDB serialises `readwrite` transactions whose scopes overlap.
    So with both writes scoped this way, a save and a delete in two tabs
    can't interleave: whichever runs second sees the first's result.
  - `validateExpense` in the form is for the user's feedback only. The
    transaction's check is the guarantee. `BroadcastChannel` (H2) only
    refreshes the other tab's lists; it is not concurrency control.
- **Saving.** Writes happen at once; there is no separate save-file step.
- **Reads.** Every record goes through a reader in the style of
  `draft.ts`: shape check, then validation (H4).
  - A record that fails is **never deleted or rewritten**. It is skipped,
    and the household shows "1 expense couldn't be read" with a
    plural-aware count.
  - The point is that a bug or a partial write can never cost the user
    data silently.

### H2 — A versioned schema, a migration runner, tested

**The runner.** `app/src/data/migrations.ts` is an ordered list of steps,
one per database version.
- `onupgradeneeded` runs every step from `oldVersion + 1` to the current
  version, in the upgrade transaction.
- Version 1 creates the stores and indexes above, and writes
  `meta.schema = { version: 1, migratedAt }`.
- The runner takes the list as a parameter, so its tests can use their
  own lists.

**Tests**, in `fake-indexeddb` (H17):
1. a fresh database is created at version 1;
2. **an app update:** a frozen version-1 snapshot (`data/fixtures/v1.json`,
   raw records as version 1 writes them) is loaded into a version-1
   database. The current code opens it, and every household, member and
   expense reads back equal. This snapshot test stays for every later
   schema change;
3. the runner, given a test-only list with a version-2 step, upgrades a
   version-1 database with every record intact. The step adds an index
   and rewrites every record from `v: 1` to `v: 2` **with the same
   content** (R2-O1). So "reads back equal" means the same domain values,
   and the test checks that data survives an upgrade. It also stops cleanly on a step that throws: the
   upgrade transaction aborts, and the version-1 data is unchanged.

**Other tabs and versions:**
- **`versionchange`.** A newer Settle opening in another tab triggers
  `versionchange`. This tab closes its connection and shows "Settle was
  updated in another tab. Reload this page to keep going."
- **`blocked`.** An upgrade blocked by an old tab shows "Close Settle's
  other tabs to finish updating."
- **An older app.** If this tab's code is older than the database
  (`VersionError`), it shows the reload message rather than failing
  silently.
- **`BroadcastChannel('settle-data')`.** After a write, the tab posts the
  changed household id, so a second tab refreshes its lists.

### H3 — When storage isn't available

If `indexedDB` is missing or the database can't open (some private
modes, or blocked site data):
- the household pages show one state: "This browser isn't letting
  Settle save households. Your split still works." That is a `Card` with
  the reason in words;
- the split keeps working as before.

The first time a household is created, Settle calls
`navigator.storage.persist()` once, from that click. The ledger is
long-lived data, and the request asks the browser not to evict it under
storage pressure. Whatever the browser answers, the app works the same.

### H4 — The model

Everything below is pure TypeScript in `app/src/features/household/`,
with no React.

**Household:**
```
Household { v: 1, id, name, createdAt, updatedAt, archivedAt? }
```
- `name` is 1–60 characters after trimming.
- Dates are ISO timestamps.
- An archived household is hidden from the switcher, but it is listed
  under "Archived" and can be restored. There is no household delete in
  M4: a backup (M6) should exist before data can be destroyed.

**Member:**
```
Member { v: 1, id, householdId, name, position, joinedOn, leftOn? }
```
- `name` is 1–60 characters.
- `position` is the order members were added, which fixes their colour
  (`DESIGN.md`: a colour comes from position). A member who leaves keeps
  their position and colour.
- `joinedOn` and `leftOn` are dates, `YYYY-MM-DD`.
- A member is active on a date when `joinedOn ≤ date` and
  (`leftOn` is absent or `date ≤ leftOn`).
- At most 20 active members (the bill's `maxPeople`) and 50 in all.

**Expense:**
```
Expense {
  v: 1, id, householdId, description, date, category, payerId,
  split: QuickSplit | ItemisedSplit,
  receipt?: ExpenseReceipt, receiptKey?,
  createdAt, updatedAt
}
QuickSplit =
  | { kind: 'equal',   amount, memberIds }
  | { kind: 'shares',  amount, shares:   { memberId, weight }[] }  // 1–99
  | { kind: 'exact',   amount, amounts:  { memberId, amount }[] }
  | { kind: 'percent', amount, percents: { memberId, ratio }[] }  // bill ratios
ItemisedSplit = { kind: 'itemised', bill: Bill, members: { personId, memberId }[] }
ExpenseReceipt = { merchant?, merchantTaxId?, date?, total?, totalSource? }
```
- `description` is 1–80 characters.
- `date` is a real calendar date, `YYYY-MM-DD`, from 2000-01-01 to one
  year after today (L1-O3), so a typo such as year 20026 is caught.
  "Today" is passed in as a parameter wherever the model or a page needs
  it, never read inside them, so tests are not date-dependent (R2-O2). The
  `category` is a category id (H8).
- **A quick expense** stores its `amount`, in cents from 0,01 to
  1 000 000,00.
- **An itemised expense** stores no amount. Its amount and shares come
  from `computeSplit(bill)` (H5), so a stored total can never disagree
  with its items.
- `members` maps each bill person to a distinct household member.
- **Two payers (L1-O2).** An itemised expense's `payerId` is the household
  member who paid. It is separate from the bill's own `bill.payerId`,
  which `validateBill` still requires to be a person on the bill.
  `bill.payerId` is kept valid but isn't used for the expense, and
  `computeSplit`'s settlements are ignored: only its per-person totals
  are read (H5).
- `validateExpense(expense, members)` returns field-tagged errors, the
  way `validateBill` does:
  - **references:** the payer and every split member must be members of
    this household, in any state;
  - **the split must add up:** exact amounts sum to the amount, and
    percentages sum to exactly 100;
  - **an itemised bill** must pass `validateBill`.
- The model doesn't forbid a member who has left; the forms only offer
  the members active on the expense's date (H6).

### H5 — Shares are derived, never stored

`expenseShares(expense)` returns each member's share, in cents. Their sum
always equals the expense's amount.
- **equal:** `allocate(amount, [1, …])` over the chosen members;
- **shares:** `allocate(amount, weights)`;
- **exact:** the amounts as entered (validation guarantees they sum to
  the amount);
- **percent:** `allocate(amount, ratios over a common denominator of
  1000)`. This uses exact integers, as M1 does;
- **itemised:** `computeSplit(bill)`'s per-person totals, through the
  person-to-member map.

**Tie-break, quick splits.** Leftover cents go to the largest
remainders. Ties go in member order, **rotated by a stable hash of the
expense id**. An itemised expense keeps `computeSplit`'s own single
rounding, unchanged. So over a
household's many equal splits, nobody absorbs every leftover cent. That
is the household version of M1's fairness note.

**Totals.** An expense's amount and a month's total are always computed
from the stored expenses, never stored. M5's balances will be derived the
same way.

### H6 — Who paid, and who shares

- **The payer** is any member active on the expense's date, whether or
  not they share in it.
- **The split** offers the members active on that date, all ticked by
  default.
- **Editing an older expense** also offers the members already on it, so
  a member who has since left still shows on their past expenses and can
  be kept.

### H7 — Members leaving and joining

- **"Mark as left"** asks for the date (today by default) and sets
  `leftOn`. The member stays in every past expense, in its history and
  filters, and in the member list under "Left", with the date.
- **"Undo leaving"** clears `leftOn`. That also covers a member who
  comes back after a gap: they then count as active during the gap too
  (L1-O4). Activity only decides which members the forms offer (H6),
  never shares or totals, so this is safe. M5 must not treat membership
  periods as exact.
- **A new member** can be added at any time, with `joinedOn` today
  (editable).
- **Deleting a member** is offered only while they appear in no expense,
  as a payer or in a split. The repository check is conservative (H1,
  M-I-4): an unreadable expense in the household also blocks it, and
  "Mark as left" is offered instead.

### H8 — Categories

A fixed list:
- Groceries, Eating out, Rent, Utilities, Internet, Household, Transport,
  Leisure and Other;
- stored as ids (`groceries`, `eatingOut`, …) and translated in the
  catalogue;
- each with a Tabler icon, shown beside its words.

Custom categories are a "Useful" item and are left out (Out of scope).

### H10 — Itemised expenses: the split, saved into a household

**Saving a split.** When the bill is valid, The split step (and the
beside layout) gains "Save to a household". It opens a dialog with:
- **the household:** the last used, or a choice. With none, the dialog
  offers to create one;
- **who is who:** each bill person matched to a member;
  - Names are matched case- and accent-insensitively by default.
  - Anyone unmatched must be chosen, or "Add as a new member".
  - Two people can't be the same member.
- **who paid:** any member, defaulting to the bill's payer's member;
- **what, when, which category:** the description (the receipt's
  merchant, or empty to fill in), the date (the receipt's, or today) and
  the category (Groceries after a scan, else Other);
- the duplicate check (H11).

**After saving:**
- The expense is created, and the draft is cleared, as New bill does.
  The draft is cleared **only once the expense's write transaction has
  completed** (L1-O1). A failed write (a full disk, `versionchange`,
  storage blocked) keeps the draft and shows the error, so a bill is
  never lost between the two stores.
- The page opens the new expense.
- The bill has *become* the expense, so saving twice can't happen by
  accident. The dialog says this before saving, in its visible text next
  to the Save button: "The bill moves into the household. The split
  starts fresh after saving." (O-EXT-2). Cancel, Escape or closing the
  dialog changes nothing: the draft stays as it was. Tests check both.

**Splitting a bill from a household.**
- "Add expense" offers "Quick expense" and "Split a bill".
- "Split a bill" opens `/split?household=:hid`.
  - With a draft that has content, it first asks to replace it (New
    bill's confirmation).
  - Otherwise it starts a bill whose people are the household's active
    members, in order, and whose payer is the first of them.
- **Too few members (M-I-2).** A bill needs at least one person
  (`LIMITS.minPeople` is 1, `model.ts`:61) and a payer among them.
  - **With no active member**, "Quick expense" and "Split a bill" are
    disabled, with "Add the people who share costs first" and a link to
    Members. That covers a new household, and one whose members have all
    left.
  - **With one active member**, both work. The seeded bill has that one
    person, a valid bill as today. More people can be added in the split
    and matched on saving.
  - **When the active count drops** (a member marked as left), the
    buttons follow at once, from the same data.
  - Saving a split into a household with no active member works through
    "Add as a new member" in the save dialog, so the dialog never offers
    an empty choice.
  - Tests: 0, 1 and 2 active members, and 1 → 0 after "Mark as left".
- The person-to-member link is kept in memory, and the save dialog starts
  from it. After a reload, the name matching above restores it, since
  the names are the members'.

**Editing an itemised expense.**
- The expense page's "Edit items" opens `/split?expense=:eid`. The split
  page then edits a **working copy** of that expense's bill, held in
  memory.
- The draft in `settle.bill` is untouched, so a split in progress is
  never lost.
- **How (L1-O2).** `useBill` gains a source parameter: the draft (the
  default, today's behaviour, unchanged for every existing caller and
  test) or an in-memory working copy, which reads from the expense and
  saves nowhere until "Save changes". Tests cover both sources, and the
  existing split suites run unchanged on the default.
- A banner names the expense, with "Save changes" and "Cancel". New bill
  is hidden.
- A person added while editing is matched as above.
- A reload discards the unsaved edits and returns the expense unchanged.
  The banner says so.

### H11 — The duplicate-receipt warning

A receipt key follows these rules, in order (when it is computed is
below):
1. **With a fiscal QR code and an ATCUD:**
   `qr:<issuer NIF>:<ATCUD>`. The ATCUD identifies one Portuguese fiscal
   document.
2. **With a QR code but no ATCUD:**
   `qr:<NIF>:<document type>:<date>:<total>`.
3. **Without a QR code:** `m:<merchant, case- and accent-folded>:<date>:<total>`,
   only when all three are known.
4. Otherwise no key, and no check.

**When the key is computed (M-I-1).** Rules 1 and 2 need the QR code's
ATCUD and document type, which today's `ReceiptSummary` doesn't keep. So
the key is computed **at import**, while the parsed `FiscalQr` is in hand
(`toBill.ts`, where `qr.issuerNif` is read today), and stored:
- `ReceiptSummary` gains an optional `receiptKey` string, set at import
  by rules 1 to 3. It is additive: the reader accepts it only when it
  matches `^(qr|m):` and is at most 200 characters, else reads it as
  absent. `RECEIPT_VERSION` stays 1;
- so the key survives a reload exactly as computed, with no QR metadata
  to rebuild later;
- **a summary saved before M4** has no `receiptKey`. On saving, the key
  is computed from what it does keep, which is rule 3 only (merchant,
  date and total). A summary without a QR code can never produce a `qr:`
  key, so an old summary can't take a wrong branch;
- the expense stores the key (`receiptKey`) and its `ExpenseReceipt`
  (merchant, NIF, date, total and its source) for display;
- tests:
  - a QR code with an ATCUD, and one without, each: import, reload,
    save, then a second save warns;
  - an old summary (no `receiptKey`) takes rule 3, or no key when the
    merchant, date or total is missing;
  - an invalid stored `receiptKey` reads as absent.

**Wording (O-EXT-1).** The warning stays advisory and says "looks
already saved", never "is a duplicate". It is **not** a uniqueness
constraint: the check runs before the save, outside its transaction, so
another tab can save the same receipt in between. That is accepted. The
copy never claims a receipt is unique or "not yet saved". Rule 3 can match two genuine
purchases of the same total at the same shop on one day, so "Save
anyway" is always offered, and is the default focus only in that case.

**The check.** Before the save, the household's `byReceiptKey` index is
checked. If an expense already has the key, a warning dialog names it:
"This receipt looks already saved: Continente, 14 Oct, 38,47 €." It offers
"Save anyway", "Cancel" and "Open that expense". It never blocks the
save.

### H12 — History (the Expenses tab)

**The list.**
- Expenses are grouped by month, newest first. Within a day, the latest
  created comes first.
- Each row shows the date, the description, "(11 items)" for an
  itemised expense, the category with its icon, the payer's badge and
  the amount.
- A row is a link to the expense.

**Filters.**
- **Member:** paid by them, or sharing in it.
- **Category.**
- **Search:** the description, the receipt's merchant, item names and
  the category's name in the current language. The search is case- and
  accent-insensitive (NFD, combining marks removed), so "agua" finds
  "Água".

The filters live in the URL, so Back and a reload keep them. A filter
that hides everything says so, with a way to clear it.

**Performance.** The whole household's expenses are read once and
filtered in memory. The test keeps the list responsive at 1000 expenses
(render and filter in jsdom under a set time). Paging is left for when
real use needs it.

### H13 — The household overview

The overview covers one month at a time (`?month=YYYY-MM`, the current
month by default, with previous and next links). The current month comes

### H16 — The split draft and "the draft into the new model"

The roadmap asks for M1's `settle.bill` draft to be "migrated into the
new model". This plan reads that as follows:
- **The draft stays as it is.** It remains the split's working copy in
  `localStorage`, same key and format, loaded synchronously as today.
- **Its bill becomes an expense** when the user saves it into a
  household (H10). That is the one way a draft enters the ledger.
- **A draft saved before M4** is read as before and can be saved into a
  household the same way.

Moving the draft itself into IndexedDB would make the split's first
render asynchronous and its tests harder, and buy nothing: the draft is
scratch data, not ledger data. This reading is listed under Open
questions for the reviewer.

## Acceptance targets

- **The completion scenario (roadmap, REQ-11)** is an integration test
  over the real repositories and `fake-indexeddb`:
  - a household with 4 members;
  - 34 expenses, 24 quick (all four methods) and 10 itemised (one with a
    receipt summary and `receiptKey`), so 31 remain after the deletes;
  - a member who leaves mid-way, and a fifth who joins;
  - six corrections: three edits (amount, payer, split) and three
    deletes.

  The test then:
  1. closes and reopens the database (a reload), and every expense,
     member and household reads back equal, with the same derived shares
     and month totals;
  2. **an app update (L1-I1):** the scenario's database is upgraded
     through the test-only version-1 to version-2 migration (H2, test
     3), and every household, member and expense, the derived shares and
     the month totals read back equal after it;
  3. **a fixture round trip:** the raw records are exported, loaded into
     a fresh version-1 database and reopened. Everything reads back
     equal. At version 1 this is the same code path as a reload, so it is
     named a round trip, not an update;
  4. confirms the version-1 snapshot fixture (H2) reads back equal.
- **Exactness (REQ-11).** `expenseShares` is unit-tested with M1's
  guarantees, for every split kind:
  - the shares sum exactly to the amount;
  - no share is negative;
  - equal weights differ by at most one cent;
  - the rotation is deterministic for an id;
  - 0,01 split three ways gives one cent to exactly one member;
  - 1 000 000,00 split by 99/1 weights is exact;
  - percentages with three decimals summing to 100 are exact;
  - exact amounts that don't add up are rejected, and so are
    percentages that don't sum to 100.

  A property-style test runs 2000 seeded random expenses of every kind
  and checks the sum invariant.
- **Data integrity:**
  - **unreadable records:** a record that fails its reader is skipped,
    counted and left in the database, byte for byte;
  - **deleting a member** with expenses is refused inside the
    transaction;
  - **unreadable records and deletes (M-I-4):**
    - a preserved, unreadable expense that names the member blocks the
      delete;
    - so does an expense with an unsupported record version (`v: 99`),
      and one with no readable `householdId`;
    - after each refusal, the member and the raw expense are byte for
      byte unchanged;
    - an unreadable expense of **another** household doesn't block;
  - **two tabs (M-I-3)**, simulated with two connections to one
    database:
    - an expense saved after its member was deleted elsewhere is refused
      and writes nothing;
    - a member deleted after an expense naming them was saved elsewhere
      is refused;
    - with the two transactions started together, exactly one of the
      outcomes above happens, never an orphaned reference;
  - **a failed upgrade step** leaves version-1 data intact;
  - **other tabs:** `versionchange` closes the connection and shows the
    reload message.
- **The existing behaviour is kept:**
  - the full `npm run check` suite passes;
  - the split's suites keep their assertions. Only harness additions are
    allowed (a provider around the page), as in M3;
  - the CI browser smoke test (scan, `--expect-bill`) still passes on
    the production build;
  - a split with no household is unchanged.
- **Both languages:** every new page renders in Portuguese with no
  English sentinel, the category and filter labels are asserted exactly,
  and the literal-text guard passes.
- **Design:**
  - every new screen at 360, 390, 1024 and 1440 px in both themes, with
    no sideways scroll at 360 px and a focus ring on every Tab stop
    (`screens.mjs` extended);
  - the Impeccable detector and ux-lint clean, or each finding reasoned
    in `CHECKS.md`;
  - one accent per screen.
- **Privacy:** `check-requests.mjs page-load` and `scan` pass on the
  production build, every request same-origin. The CSP is unchanged.
- **Performance:** 1000 expenses render and filter within the test's
  budget (H12). The first-view font and bundle budgets in
  `check-build.mjs` still pass.

## Migration, data and backup implications

- **New:** the IndexedDB database `settle`, version 1, and the
  `settle.household` pointer, which is an id only.
- **Unchanged:** `settle.bill`, `settle.receipt`, `settle.theme`,
  `settle.region` and `settle.language` keep their formats.
  `ReceiptSummary` gains an optional `receiptKey`, read by the same
  version 1 reader (H11).
- **No data is migrated automatically.** A draft enters the ledger only
  when the user saves it (H16).
- **No backup exists until M6.** M4 therefore never destroys ledger data
  without the user's explicit, confirmed action:
  - no household delete;
  - expense delete with a confirmation;
  - member delete only when unused;
  - unreadable records kept.
- **Eviction risk.** Clearing site data deletes the ledger.
  `navigator.storage.persist()` lowers the risk of eviction (H3), and M6's
  export is the real answer. Settings' existing line, "stored on this
  device", stays true.

## Out of scope

- Balances, who owes whom, settling up and "Mark as paid" (M5).
- Export, import, backup and sharing between devices (M6).
- From the roadmap's "Useful" list: custom categories, notes, an attached
  receipt image, and undo for delete. Deletes are confirmed instead.
- Recurring expenses, multi-currency households (Future).
- Household delete (after M6's backup).
- Properties, units and tenants (M17).
- Any change to the split maths, the parser or the reader.

## Stop conditions

Stop and ask the user if:
- an existing split test's assertions would have to change (not only its
  harness);
- the CSP would need a new source;
